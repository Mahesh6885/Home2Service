# MultiWork — Risk Register & Mitigation Strategy

| Risk ID | Category | Description | Likelihood | Impact | Mitigation Strategy | Owner |
|---|---|---|---|---|---|---|
| **RSK-01** | Technical | **Race condition on broadcast worker acceptance:** Multiple workers clicking accept simultaneously could double-assign a job. | High | Critical | Enforce atomic DB transaction with `select_for_update()` row locking on the `Booking` and `WorkerOffer` records. Only the first commit succeeds; subsequent requests return HTTP 409 Conflict. | Backend Lead |
| **RSK-02** | Geographic | **Inaccurate location or spoofed coordinates:** Workers or customers providing coordinates outside Coimbatore or inaccurate points. | Medium | High | Implement server-side bounding box validation for Coimbatore coordinates and Haversine formula calculation. Validate coordinates before creating bookings or updating worker positions. | Backend Lead |
| **RSK-03** | Performance | **Polling overhead on DB:** Frequent polling by workers and customers for offer updates and booking states could load the database. | Medium | Medium | Use optimized, indexed query endpoints (`is_read=False`, `status='PENDING'`) with lightweight JSON responses. Use 3–5s intervals only when active requests are open. | Backend / Frontend |
| **RSK-04** | Security | **Broken Object-Level Authorization (BOLA):** Workers viewing customer private contact/address details before assignment or modifying other workers' quotes. | High | Critical | Enforce strict DRF object-level permissions (`IsAssignedWorker`, `IsBookingOwner`) on every retrieve and update view. Strip exact address fields until assignment is confirmed. | Security Lead |
| **RSK-05** | Schedule | **Scope creep (payment gateway / WebSockets / real-time tracking):** Integrating premature paid external services risking the 20 October 2026 deadline. | High | High | Keep payment gateway explicitly deferred beyond MVP (quotation-based price record only). Use reliable HTTP polling rather than complex WebSocket infrastructure. | Project Lead |
| **RSK-06** | Operational | **Worker shortage in 5 km radius:** In low-density service areas in Coimbatore, 5 km might yield zero workers. | High | Medium | Provide clear feedback in UI when 0 workers are found. Allow explicit user-initiated retry or documented policy recommendation for radius expansion rather than silent auto-expansion. | Product Lead |
| **RSK-07** | Reliability | **Notification spam and duplicate alerts upon network retries:** Clients resubmitting requests creating duplicated notifications. | Medium | Medium | Implemented deterministic `idempotency_key` unique constraints on `Notification` model, ensuring repeat dispatches or state sweeps resolve to existing notifications without duplicates. | Backend Lead |
| **RSK-08** | Compliance | **Sensitive personal or auth credential leakage in audit logs:** Passwords, tokens, or exact identity numbers leaked into audit metadata. | Medium | Critical | Implemented `sanitize_metadata()` filtering in `apps.notifications.services` stripping passwords, JWT tokens, street addresses, and ID numbers before persistence. Restrict audit endpoint strictly to admin roles. | Security Lead |
| **RSK-09** | Privacy | **Uncontrolled live location tracking exposure:** Tracking coordinates exposed before assignment or after job completion. | High | Critical | Server enforces strict lifecycle guards: tracking returns `is_location_available=False` prior to assignment and automatically ceases upon completion/cancellation. Workers have one-click pause control. | Security Lead |
| **RSK-10** | Performance | **GPS update abuse / battery drain:** Rapid location pings exhausting battery or overloading server. | Medium | Medium | Implemented 5-second server throttle with HTTP 429 backoff, 30s background sync interval while tab is active, and polite 12s customer poll interval. | Fullstack Lead |
